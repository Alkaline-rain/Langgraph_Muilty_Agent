# 项目知识与面试问答

依据：2026-10-04 当前仓库源码及 [验证记录](../VALIDATION.md)。本文中的“已实现”指代码能力，“已验证”以已有测试记录为准；没有真实 LLM 成功率或成本提升结论。

建议使用方式：先能够不看文档讲清全流程，再顺着源码回答问题，最后亲手做几个故障实验。回答提示用于理解，不建议逐字背诵。

## 一、必须先记住的项目边界

- 输入：自然语言任务及人工维护的可信 JSON 用例。
- 输出：实现 `solve(payload)` 的单文件 Python 代码、验收结果和执行轨迹。
- 生成、审查、反思：宿主侧调用模型；候选代码：容器内禁网执行。
- 三个模型角色、四个图节点；execute 是确定性程序，不是 LLM Agent。
- 主流程成功：任务提供的全部开发验收用例通过。评测最终成功：开发验收和最终保留用例都通过。
- 当前不包含多文件仓库编辑、在线依赖安装、服务并发队列、RAG 检索或自动断点续跑。
- 最近实测：2026-10-02，55 项回归通过、0 跳过；24 个参考实现的 72 个用例已在 Docker 验证。两轮修复演示使用固定 Agent 替身。

## 二、从代码入口讲完整条链路

```text
任务与配置校验 → 建立运行目录 → Docker 环境预检
                                  ↓
                              generate
                                  ↓
                execute：语法/AST → Docker → 宿主可信比较
                    ├─ 通过 → END
                    ├─ 环境错误/次数或预算耗尽 → END
                    ├─ 首次简单错误 → generate
                    └─ 复杂或重复错误 → review → reflect → generate

每轮保留：代码、验收、失败指纹、调用用量、事件、状态快照
benchmark：开发验收通过 → 最终保留验收 → 汇总指标
```

这是默认 adaptive 的简图；review 和 reflect 后也会检查预算等终止条件。实际终止原因有优先级，不能只背图。

## 三、P0：面试前必须能够解释的问题

### 1. 这个项目解决什么问题？难点在哪里？

解决生成代码的语法、运行与逻辑错误，以及失败后反复产生无效修复的问题。难点不是让模型输出代码，而是定义可靠成功标准、隔离执行风险、控制循环成本、保留可定位的失败证据。用这四件事介绍项目，比泛泛说“用了多智能体”更有内容。

### 2. 为什么用 LangGraph？while 循环不行吗？

可以用 while 循环实现这个规模的原型。LangGraph 的价值是把共享状态、节点职责和条件路由显式化，方便加入预算、重复错误、不同修复策略和轨迹观察。代价是多一层框架与状态约定；不要声称框架本身提高生成质量。

### 3. 哪些是 Agent？为什么需要三个？

Coder 生成代码；Reviewer 分析失败和提出建议；Reflector 提炼根因和下一轮策略。它们是角色与提示词分工，可以使用同一个底层模型，并非三个独立训练的模型。execute 调用确定性验证工具。分工是否优于直接修复，需要对照实验，当前尚无真实效果结论。

### 4. State 里放什么？为什么不用全局变量？

状态包含任务、当前代码、历史版本、执行结果、验收结果、审查反思、失败记录、迭代次数、预算和终止原因。显式状态让节点输入输出、测试与快照更清楚。当前是顺序流程，历史通过节点返回新列表更新；没有依赖并发 reducer 做列表合并。

`TypedDict` 主要提供类型提示，不会自动对所有运行时赋值做校验；Pydantic 负责具体边界对象的运行时验证。不要把两者混淆。

### 5. 成功怎么判断？为什么不能让 Reviewer 决定？

候选代码必须返回可解析的 JSON，且与人工可信用例的预期一致。Reviewer 的 `passes` 是意见，不能覆盖测试失败。模型会遗漏问题或产生错误判断，独立验收能给出可复查证据，但有限用例仍不能证明任意输入都正确。

### 6. 测试答案会不会泄露给模型？

可信预期输出不进入 Agent 提示词，也不挂载到容器。容器只接收当前输入，宿主保留预期并做比较。失败诊断会提供受控反馈，这是开发反馈闭环的一部分；最终保留用例不回流修复。任务要求本身可能包含示例，不能因此宣称数据绝对保密。

### 7. 语法、AST 和运行验证有什么区别？

语法解析检查代码结构；compile 补充发现某些上下文非法用法；AST 遍历约束导入和禁止操作；运行阶段发现依赖、异常、超时；可信比较发现程序正常退出但答案错误的情况。静态通过不代表运行正确，正常退出也不代表任务成功。

这里 Python 的 `compile` 不等于执行代码；LangGraph 的图 `compile` 则是构建可运行图，二者不是同一件事。

### 8. 为什么不用 exec 加 try/except？

try/except 只能处理部分异常，不能隔离文件访问、网络、进程资源和死循环。候选代码不能在宿主进程内执行。项目禁用了旧的宿主执行降级路径，Docker 不可用时直接报告环境问题，不能为了演示成功牺牲隔离边界。

### 9. Docker 做了哪些限制？分别防什么？

| 配置 | 作用与边界 |
|---|---|
| 每用例新容器、代码目录只读 | 降低跨用例污染、避免改写输入代码 |
| `--network none` | 候选代码不能正常连接外部网络；模型调用在宿主 |
| 非 root、drop ALL、no-new-privileges | 降低权限和提权面 |
| 根文件系统只读、临时 tmpfs | 约束写入位置；临时目录不是永久存储 |
| 256 MiB 内存、同值 memory-swap | 约束内存与额外交换空间使用 |
| 0.5 CPU、64 PIDs | 限制 CPU 配额与进程数量，不等于绑定半个物理核 |
| 容器 10 秒、宿主 15 秒超时 | 防止候选代码和 Docker 调用长期占用 |
| stdout/stderr 各 64 KiB 上限 | 防止输出洪泛撑爆宿主采集内存 |
| 最终清理且清理有超时 | 避免遗留容器；无法确认清理则报环境错误 |

镜像预装固定依赖，运行时不自动拉镜像、不在线 pip install；不挂载仓库和 `.env`，不传模型密钥。真实探针检查过这些内核配置，但它不是容器逃逸防御的完整安全证明。

### 10. 默认修复路由怎么选？

adaptive 首次语法、导入或静态安全策略错误直接回 Coder；复杂错误或重复失败进入 Reviewer → Reflector。重复错误达到阈值则停止。动机是简单错误可能无需两次额外模型调用，但节省多少、是否影响通过率还需要真实实验。

### 11. 怎样判断重复错误？

错误类型、失败用例名、规范化消息一起哈希；去掉路径、行号、内存地址等不稳定噪声。重复次数按一次工作流内该指纹累计出现次数计算，不要求连续出现。它是启发式分组，不证明两次错误根因相同。

### 12. 错误指纹和代码指纹一样吗？

不一样。错误指纹用于统计同类失败与路由；代码指纹通过不含位置属性的 AST 识别结构一致的代码，语法错误时回退源码哈希。AST 指纹忽略注释和排版，但变量改名会改变指纹。当前记录代码指纹用于分析，**没有实现执行结果缓存或自动跳过相同代码**。

### 13. Self-Reflection 的输入输出是什么？能保证改善吗？

输入包括失败代码、执行错误、审查意见和有限历史；输出用结构化字段表达根因、新方案与关键修改。下一轮 Coder 接收这些建议。反思也可能误判或空泛，因此最终仍以测试为准，并用预算和重复失败终止避免无休止循环。

### 14. 如何防止无限循环？

同时限制总生成次数、逻辑模型调用次数、预算 Token、重复失败次数；执行本身还有超时与输出限制。环境和模型服务错误直接终止，不交给 Coder 修复。`max_iterations=3` 表示最多生成三版，最多两次生成后的修复机会。

最后一次获准生成的代码仍然执行验收，不能因调用次数刚好达到上限而直接丢弃。若多个停止条件同时满足，按 `termination_reason` 的实现顺序决定原因，例如生成次数上限优先于重复失败上限。

### 15. 什么是 Pydantic 结构化输出？能保证代码正确吗？

用 schema 约定 Coder 的 prefix/imports/code、Reviewer 的 passes/issues/suggestions 和 Reflector 的 root_cause/new_approach/key_changes。它帮助发现缺字段、类型错误和解析失败，不保证内容正确，也不保证模型每次都遵守协议。解析失败归入模型错误；已发生的调用仍要记账。

### 16. LCEL 在哪里？是不是用了 LCEL 就用了 LangGraph？

LCEL 用于表达 LangChain Runnable 的组合，例如 prompt → 模型 → 输出解析器；LangGraph 管理带状态、分支和循环的流程。当前候选 LCEL 任务使用 FakeListLLM 或 RunnableLambda 离线运行。行为用例通过不证明实现内部一定用了 LCEL；强制框架使用需要另设检查。

### 17. 项目有 RAG 吗？记忆是什么？

主流程使用本地固定的离线文档上下文，没有向量索引或在线检索，因此不应包装为 RAG。这里的“记忆”主要是单次工作流的代码与失败历史，不是跨用户长期记忆，也不是训练模型权重。

### 18. 如何证明项目真正跑过？

展示测试报告、真实 Docker 探针、独立运行目录、两版代码和第一次失败/第二次通过的验收记录。主动说明该两轮演示的 Agent 是固定替身。它验证图和执行器的连接；真实模型效果需要 live 实验，不能拿模拟通过率替代。

## 四、P1：深入追问与工程取舍

### 19. 为什么每个用例都启动新容器？性能怎么办？

新容器简化隔离和清理，避免前一用例的全局变量、文件等影响下一例；代价是启动开销大。当前用例少、优先正确隔离。未来可以研究一任务一容器或池化，但要重新处理状态重置、取消、资源回收与跨任务污染，不能只改成复用就宣称优化完成。

### 20. 为什么既有容器内超时又有宿主超时？

容器内限制用户程序的运行时间；宿主兜底限制整个 CLI 调用等待时间，两者覆盖范围不同。杀掉 Docker CLI 不等于一定杀掉容器，所以还需要按唯一名称执行有界清理。清理失败必须保留容器名和错误，不能报告完全成功。

### 21. 输出采集为什么也会出问题？

无限打印会耗内存；只读 stdout、不读 stderr 还可能因管道写满导致阻塞。当前分别读取两个通道，设置字节上限，超限终止并执行清理。保存到验收明细的文本还会进一步截断；保存日志限额与进程输出限额是两个层次。

### 22. stdout 混入 print 怎么办？

可信 runner 把普通候选 print 重定向到诊断通道，将 `solve` 返回值序列化到结果通道；宿主再解析和比较。恶意或异常行为仍可能破坏协议，因此解析失败也要判失败。不能靠“程序说自己通过了”或 stdout 内异常关键词决定结果。

### 23. JSON 相等有什么坑？

Python 中 `True == 1`，但任务协议把布尔与数值区分；1 和 1.0 可以视为数值相等。对象键顺序不重要，数组顺序重要；不接受非有限数值，也没有浮点容差比较。协议不明确会导致误判，所以这些要有边界测试。

### 24. AST 白名单够安全吗？Docker 是虚拟机吗？

AST 规则只覆盖部分危险结构，动态语言行为和允许库的间接能力很难靠它完全判断。容器依赖 Linux 内核隔离；Windows Docker Desktop 使用 WSL2 的 Linux 环境，候选容器仍共享该 Linux 内核。项目提供分层风险限制，不承诺抵御所有内核漏洞或达到生产多租户安全标准。

### 25. 退出码 137 是不是内存溢出？

137 表示 SIGKILL 对应的退出状态，可能由 OOM、超时强杀或外部终止引起，不能只凭退出码断言 OOM。应结合执行时间、错误信息及可获得的容器状态。当前分类描述要保持这一边界。

### 26. Token 预算怎么做？真的是硬上限吗？

调用前检查次数，再以提示词和 schema 的 UTF-8 字节估计、额外余量和最大输出预留预算；返回后优先使用厂商 usage 记实际用量。缺失 usage 或失败时保守扣预留额，实际 usage 保持未知而不是填零。这不是厂商 tokenizer，也不是账单硬上限；实际超估计后会记录实际值并限制后续调用。

### 27. 一次图调用等于一次模型请求吗？

不是。一次工作流包含多轮生成、审查、反思；每次逻辑模型调用也可能在校验阶段被拒绝。项目关闭 SDK 自动重试，并用 `request_started` 记录是否进入请求；真实账单仍应结合厂商 usage，不能把逻辑调用数当成精确计费请求数。

### 28. 历史越多越好吗？怎么截断？

全量代码反复注入会增大成本、延迟并引入噪声。当前优先保留最近代码、最新错误与建议、最近三次失败摘要，反馈默认最多 6000 字符，整个提示词最多 20000 字符。本地仍保存完整历史。它是字符裁剪，不是语义摘要模型，也不等同于 Token 计数；原问题过长时拒绝调用而非静默截断。

### 29. 日志存了什么？如何定位一次失败？

先看 manifest 的状态与终止原因，再看 state 的 attempt_history、failure_trail 和 code 版本；call_history 区分模型错误及 usage；events 定位最后完成的节点。每次运行独立目录，避免覆盖。注意业务输入和候选输出仍可能含敏感信息，不能把“不保存 .env”理解成日志天然不含敏感数据。

### 30. 原子快照是什么？等于断点恢复吗？

先写临时文件并 flush/fsync，再用 os.replace 替换 state.json，减少读到半份 JSON 的风险。事件逐条追加落盘；快照保存最后完成节点的状态。它不等于数据库事务，也没有实现 LangGraph checkpointer 或自动续跑。强杀时可能保留 running 状态，磁盘故障也无法保证记录完整。

### 31. 模型限流和代码报错为什么要分开？

认证、限流、连接、超时或结构化解析失败属于模型服务/调用问题；语法、运行、测试失败属于候选代码问题。让 Coder 修复 API 限流只会消耗无效调用。项目细分模型错误码并终止，供应商异常仅保留类别，避免把含请求细节的原始异常写入日志。

### 32. 为什么同时有 exec_error_type 和 termination_reason？

前者解释当前执行或工作流出了什么问题，后者解释为什么最终停止。例如最后一次生成出现 test_failure，最终原因可能是 max_iterations。只保留一个字段会混淆代码质量问题和资源控制决策。

### 33. 既然有 ContextVar，是不是支持并发服务？

它隔离调用上下文中的记账信息，但不意味着已实现任务队列、全局并发限额、取消传播或 API 服务。当前是命令行工作流。后续服务化需要额外设计鉴权、队列、工作进程、全局资源预算、幂等、状态存储和故障恢复。

## 五、P1：评测设计，最容易被追问的部分

### 34. 四种策略各自验证什么？

| 策略 | 行为 | 要回答的问题 |
|---|---|---|
| single | 一次生成 | 基础生成能力怎样？ |
| direct | 错误直接反馈 Coder | 单纯多试几次是否就够？ |
| full | 每次失败都审查和反思 | 额外角色是否带来收益？ |
| adaptive | 简单错误直修，复杂/重复错误反思 | 条件调用是否更划算？ |

只有 full 对 single 的提升不足以证明反思有效，因为额外预算也能带来提升。必须与 direct 比较，并同时报告实际成本。

### 35. 怎么让对照公平？

固定任务、模型、角色温度、执行环境、验收标准与上下文规则。采用相同生成次数上限时报告额外审查成本；采用相同调用上限时允许 direct 把更多预算用于生成。两种口径回答不同问题，预算上限相等也不等于实际费用相等。固定 seed 仅固定运行顺序，不控制厂商模型随机性。

### 36. 为什么分开发用例和保留用例？

开发用例的失败用于迭代，反复接触会产生针对用例修补的风险。最终保留用例只在开发通过后执行且不反馈，提供额外泛化检查。当前每题只有一个保留用例，24 题也是小型自建集，不能外推为通用代码能力。保留集在仓库中可见，更不能称作从未泄露的权威测试集。

### 37. 通过率、修复成功率怎么算？

- 全体通过率：开发与保留均通过的运行数 / 全部已完成运行数。
- 有效运行通过率：排除环境、任务和模型等非代码异常后的通过率；同时报告排除数量。
- 修复成功率：首次开发失败、最终全部通过的有效运行数 / 首次开发失败的有效运行数。
- 重复错误率：同一运行内同指纹再次出现的失败次数 / 有效运行的失败总次数。
- 平均修复轮次：平均 `max(生成次数 - 1, 0)`，包括最终失败运行。

回答时先说清分母。分母为零时按实现报告为空值等约定，不能凭空解释为 100%。

### 38. 96 次模拟能证明什么？55 项测试又证明什么？

96 次模拟验证四策略在固定故障剧本下的路由、记账和汇总管线。55 项回归覆盖业务边界、工作流与真实 Docker 集成；其中一项遍历参考任务的 72 个用例。这些不是 96 次真实模型实验，也不是 55 个独立模型题目，不能推导真实修复成功率。

### 39. 多次重复实验是不是样本量大了？

同一题重复生成有助于观察随机波动，但并未增加题目多样性，不能把重复运行当成新增独立任务。优先按同题、同重复编号做配对比较，报告原始记录与波动；若要更强结论，需要扩大任务覆盖、增加保留用例并进一步做统计分析。当前没有已完成的显著性检验。

### 40. 如果 adaptive 不如 direct 怎么解释？

可能任务太简单、反思建议不准、额外角色耗尽预算、错误分类粗糙或上下文裁剪损失信息。先核对有效样本与预算口径，再按错误类型和任务类别分析，不删掉失败记录。项目价值也包括发现在哪些场景简单方法更有效。

## 六、P2：可以讨论，但尚未实现的扩展

### 41. 下一步最值得做什么？

先补一题真实模型 smoke 和小规模 live，再完成四策略真实对照。之后根据证据改进路由或任务覆盖。真实效果未验证前，增加更多 Agent、接入向量库或做复杂前端未必解决核心问题。

### 42. 如果扩展到真实多文件代码仓库？

需要工作目录与文件变更协议、补丁应用与回滚、项目依赖构建、测试发现、版本控制、上下文选择以及更严格的执行授权。现在的 `solve(payload)` 和固定 JSON 比较可以作为受限任务协议，但不足以直接支持仓库开发。

### 43. 如果支持在线 API 任务？

需要区分模型访问与候选代码访问，设计目的地址限制、受控网络代理、凭据注入范围和审计，而不是直接取消禁网。对外写入还涉及动作授权和重试幂等。当前离线范围是主动控制问题规模的取舍。

### 44. 如果把错误指纹升级为缓存？

缓存键不能只含代码：还需要输入、依赖镜像身份、执行配置和协议版本等；还要考虑非确定性代码、失败缓存有效期以及环境错误不能当代码失败复用。当前只记录指纹，没有缓存，所以面试时可以把它作为设计讨论。

### 45. 怎么优化整体耗时？

先用节点事件与调用/执行耗时定位瓶颈，区分模型延迟、容器启动、重复用例执行和日志落盘。可能的方向包括减少无效反思、对可信独立用例做有界并发、镜像构建优化；任何容器复用与并发都要重新审视隔离、全局资源和可复现性。目前未实现这些优化。

## 七、三个可用实证讲述的设计案例

### 案例 A：代码运行成功，任务却失败

场景：加法任务生成了减法，代码无异常退出。处理：宿主可信比较判为 test_failure，反思后第二版加法通过。可展示 [两轮记录](../runs/20261002T064802Z-1bab76f4/state.json) 和代码版本。边界：这是固定 Agent + 真实 Docker 演示，不是真实模型自主发现问题的记录。

### 案例 B：防止无效修复消耗预算

场景：相同规范化错误多次出现。处理：记录指纹次数，第二次升级 change_approach，adaptive 默认第三次可停止，同时受生成与调用预算控制。解释“可停止”：如果先触发生成次数上限，最终 reason 是 max_iterations。不要把策略目标讲成已经实测降低了多少成本。

### 案例 C：配置存在，不代表真的生效

场景：Docker 参数写进代码后仍需验证实际环境。处理：除了成功执行，还用内核探针检查 UID、capabilities、网络接口、只读文件系统和 cgroup 限额，并验证无限循环与输出洪泛。可展示 2026-10-02 测试报告。边界：检查限制生效，不等于证明不存在容器逃逸。

## 八、动手复习清单

不要把候选代码导出后直接在宿主运行。以下实验均使用现有 Docker 执行路径；固定测试不调用付费模型。

1. 不看文档画出四节点图，解释每条分支和每个停止条件，然后对照 edges.py。
2. 运行 `scripts/smoke_workflow.py`，找到两版代码、首次 test_failure、最终 tests_passed；说明 Agent 替身与真实执行器的边界。
3. 阅读一个正确答案测试与一个布尔/数值边界测试，解释为何 `True` 不能冒充 `1`。
4. 阅读 timeout 和输出限额测试，说明宿主子进程结束后为何还必须清理容器。
5. 手算一次错误指纹累计：A → B → A 时，A 已出现两次；解释它不是连续失败计数。
6. 对同一代码只改注释、再改变量名，预测 code_fingerprint 哪次变化，并在工具函数级别验证。
7. 阅读预算边界测试，解释最后一版代码为什么仍验收、结构化解析失败为什么不能记零成本。
8. 打开一份 simulation manifest 和报告，指出能说明的工程事实与不能说明的模型效果。
9. 分别用一句话解释错误类别、停止原因、开发通过与最终评测通过。
10. 完成真实调用后另保存 live 记录，再更新简历中的实验结果；保留此前失败与无效运行。

## 九、推荐准备顺序

| 阶段 | 学习目标 | 自测标准 |
|---|---|---|
| 第一遍 | P0 + 状态图 + 口述介绍 | 90 秒讲清输入、流程、验收和边界 |
| 第二遍 | 静态验证、runner、Docker、资源限制 | 能解释正常退出不等于成功，以及 Docker 不可用为何停止 |
| 第三遍 | 指纹、反思、预算、上下文 | 能手算一个三轮失败流程的路由与调用次数 |
| 第四遍 | 评测、日志、真实与模拟区别 | 能解释所有指标分母并展示一份原始记录 |
| 最后一遍 | live 验收与项目复盘 | 拿真实证据讨论收益、失败和适用范围 |

项目之外还要按岗位补 Python、数据结构与算法、操作系统/进程、网络基础，以及 LLM 应用中的上下文、结构化输出和评测基础。项目面试最重要的是能够沿着一次具体失败追到源码，而不是记住更多名词。
