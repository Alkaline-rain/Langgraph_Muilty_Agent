## 2. 可直接用于简历的版本

**基于 LangGraph 的多智能体代码生成与自动修复系统**  
技术栈：Python、LangGraph、LangChain、Pydantic、AST、Docker、LCEL

**项目简介：** 面向离线 Python / LCEL 编程任务，构建“生成—静态检查—容器执行—可信用例验收—审查反思—迭代修复”闭环，通过状态驱动路由、重复失败控制与调用预算管理，提高代码生成流程的可验证性与可追踪性。

**核心工作：**

1. 基于 LangGraph 状态图编排 Coder、Reviewer、Reflector 三类角色及确定性执行节点，根据错误类型、重复次数和剩余预算动态选择直接修复、审查反思或终止，支持 single / direct / full / adaptive 四种策略。
2. 构建语法编译、AST 规则检查与可信 JSON 用例验收流程，在宿主侧比较执行结果和预期答案，将语法、导入、运行及逻辑错误结构化反馈，避免仅凭模型审查意见判定成功。
3. 使用 Docker 实现每用例独立容器执行，配置禁网、非 root、只读文件系统、CPU / 内存 / 进程限制，并实现双层超时、输出限额和容器清理，禁止降级到宿主执行。
4. 设计错误与代码指纹、结构化失败轨迹和有限历史上下文，针对重复失败升级修复策略并提前终止；通过调用次数、输出长度与 Token 预算准入约束迭代开销。
5. 使用 Pydantic 统一角色输出，落盘逐节点事件、原子状态快照及代码版本；建立 24 题、72 用例的自建评测集与四策略对照管线，完成 55 项回归测试，其中包含真实 Docker 集成验证。

简历版面不足时，把第 4、5 点各缩短半句即可；优先保留“客观验收、隔离执行、动态修复、可复现实验”四个特点。

## 3. 60—90 秒口述介绍

> 这个项目面向单文件 Python 和离线 LCEL 任务。我关注的问题是，模型生成的代码即使能运行，也可能输出错误；让模型自己审查，还可能错误地判定通过。
>
> 所以我把最终成功条件放在可信用例验收上。LangGraph 编排生成、执行、审查和反思流程，生成代码先经过语法与 AST 检查，再放进每用例独立的 Docker 容器执行，预期答案留在宿主侧比较。
>
> 修复时，首次简单错误直接反馈给生成角色，复杂或重复错误再进入审查和反思。我记录错误指纹、代码版本和失败轨迹，并设置重复失败、调用次数和 Token 预算限制，避免无限循环。
>
> 目前工程回归有 55 项通过，也验证了真实 Docker 的执行和资源配置。我还准备了 24 题的四策略评测管线，但尚未完成真实模型对照实验，所以目前能证明的是工程链路有效，不能宣称模型成功率已经提升。

## 5. 最后一个验收缺口怎么补

操作细节见 [测试指南](TESTING.md) 和 [评测指南](../benchmarks/README.md)。以下真实调用会产生模型费用；这份文档只提供命令，未执行它们。

```powershell
# 1. 检查 Docker 和固定输入执行，不调用模型
.\.venv\Scripts\python.exe code_assistant/doctor.py --probe

# 2. 凭据配置完成后，先跑一题真实模型端到端
.\.venv\Scripts\python.exe code_assistant/main.py --task examples/add.json

# 3. 先用两题检查真实评测链路
.\.venv\Scripts\python.exe code_assistant/benchmark.py --mode live --limit 2 --repeats 1

# 4. 确认小规模记录正常后，再执行完整对照
.\.venv\Scripts\python.exe code_assistant/benchmark.py --mode live --budget-profile attempts --max-attempts 3 --max-calls 9 --repeats 3
```

最后一条包含 24 × 4 × 3 = 288 个工作流，每个至多 9 次逻辑调用，理论上限 2592 次；预算按单工作流计算，并非整批共用。先根据小规模实际 usage 估算成本，再决定实验规模。

真实实验后同时看全体通过率、有效运行通过率、修复成功率、实际调用和 Token、耗时、排除的环境或模型异常数。若 adaptive 没有优于 direct，也应如实保留结论并分析适用场景；不要为了数字好看修改评测口径。
