# 领域 RAG 升级后的项目经历（2026-10-20）

**基于 LangGraph 与领域 RAG 的代码验证和自动修复平台**

技术栈：Python、LangGraph、LangChain、Pydantic、BM25、pgvector、RRF、Reranker、Docker。

项目简介：面向单文件 Python / 离线 LCEL 代码，构建领域文档检索、任务规划、多角色修复与可信用例验收闭环，提供浏览器插件和可视化工作台，支持版本追踪与任务恢复。

1. 基于 LangGraph 实现 Planner 驱动的 Agent loop，以 Skill 封装诊断、文档检索、修复和验收，通过结构化动作、依赖与权限检查、重复动作限制及预算控制约束执行过程。
2. 设计代码围栏感知的父子分块，建立文档版本与知识快照；以子块进行 BM25 / 向量召回，经 RRF 融合、父块回填去重及可选 rerank 生成带来源和位置的知识上下文。
3. 将领域知识与历史修复经验分离，按候选镜像库版本过滤文档，在修复角色中注入有界证据；检索失败显式降级，记录实际检索模式、调用用量和证据引用。
4. 结合 AST 静态检查、受限 Docker 执行与宿主可信用例比较判定结果，代码修改后重新验收，避免以模型审查或文档相似度代替正确性判断。
5. 使用 PostgreSQL checkpoint、动作日志及代码产物管理支持中断恢复；工作台展示计划、版本差异和检索证据，插件支持代码提取与结果查看。

**表述边界：** 当前语料为项目维护的 LCEL 笔记；BM25、本地存储、真实 pgvector SQL 与容器链路可验证。外部 embedding / rerank 适配已实现，但真实服务质量和修复收益尚未完成对照实验，不能填写成功率提升或成本下降比例。没有新增缓存、消息队列或 MCP。详见 [RAG 升级指南](RAG_UPGRADE.md)。

# v2 最新简历项目经历

核对日期：2026-10-13。以下内容依据已实现代码；真实模型成功率、消融收益和费用对照尚未验证，简历不填造出的提升比例。详细证据见 [升级交付记录](UPGRADE_STATUS.md)。

**基于 LangGraph 的可规划代码验证与修复 Agent 平台**
技术栈：Python、LangGraph、Pydantic、FastAPI、PostgreSQL / pgvector、SQLAlchemy、Docker、React / TypeScript、Manifest V3

**项目简介：** 面向 LLM 生成的单文件 Python / LCEL 代码，构建“浏览器提取—任务规划—工具验证—反思修复—可信验收”闭环，提供浏览器插件与可视化工作台，支持任务恢复、跨任务经验检索和执行过程追踪。

**核心工作：**

1. 基于 LangGraph 实现 Planner 与生成、审查、反思角色协作，通过结构化动作和工具观察动态选择 Skill、更新计划；增加依赖校验、重复动作检测、调用预算和人工补充中断，约束 Agent 迭代过程。
2. 实现带版本与内容指纹的 Skill 注册体系，将诊断、修复、LCEL 检查和可信验收封装为四类能力，通过按需加载说明、Pydantic 输入输出契约及工具白名单限制执行权限。
3. 构建工作状态 checkpoint 与跨任务修复记忆，使用 PostgreSQL 持久化来源和环境版本，支持全文 / 词项检索与可选 pgvector 语义召回融合；仅将可信验收通过的修复经验写入长期记忆，支持环境过滤与删除。
4. 结合 AST 静态检查和受限 Docker 执行验证代码，通过禁网、非 root、只读文件系统、资源及输出限制控制风险；在宿主侧比较人工可信用例与容器输出，避免由模型自行宣告修复成功。
5. 使用 FastAPI 与独立 Worker 实现任务提交、取消和恢复，设计幂等键、任务租约、心跳及动作结果日志，结合 LangGraph 持久化 checkpoint 处理重启；遇到结果未知的收费动作停止重放。
6. 开发 React / Monaco 工作台及 MV3 浏览器侧栏插件，支持代码提取预览、计划与证据展示、代码 diff 和结果下载；工作台通过 SSE 序号补拉恢复事件，插件重新打开后恢复任务状态。

**验证说明（可放项目说明，不必全部写入简历）：** 完整 Python 回归 70 项通过，后续平台定向回归 15 项和新增评测测试 2 项通过；Playwright 3 项浏览器集成测试通过，覆盖真实 PostgreSQL、Docker 与实际加载的 MV3 插件。模型行为使用固定替身验证工程链路，不等同于真实 LLM 的修复效果。

**讲解边界：** 当前为本地单用户、单 Worker 原型；pgvector 使用精确距离查询，未做 ANN 索引；模型预算不包含可选外部 embedding 费用。真实模型对照实验及真实对话网站兼容性仍需补充。

## 2. 可直接用于简历的版本

**基于 LangGraph 的多智能体代码生成与自动修复系统**  
技术栈：Python、LangGraph、LangChain、Pydantic、AST、Docker、LCEL

**项目简介：** 面向离线 Python / LCEL 编程任务，构建“生成—静态检查—容器执行—可信用例验收—审查反思—迭代修复”闭环，通过状态驱动路由、重复失败控制与调用预算管理，提高代码生成流程的可验证性与可追踪性。

**核心工作：**

1. 基于 LangGraph 状态图编排 Coder、Reviewer、Reflector 三类角色及确定性执行节点，根据错误类型、重复次数和剩余预算动态选择直接修复、审查反思或终止，支持 single / direct / full / adaptive 四种策略。
2. 构建语法编译、AST 规则检查与可信 JSON 用例验收流程，在宿主侧比较执行结果和预期答案，将语法、导入、运行及逻辑错误结构化反馈，避免仅凭模型审查意见判定成功。
3. 使用 Docker 实现每用例独立容器执行，配置禁网、非 root、只读文件系统、CPU / 内存 / 进程限制，并实现双层超时、输出限额和容器清理，禁止降级到宿主执行。
4. 设计错误与代码指纹、结构化失败轨迹和有限历史上下文，针对重复失败升级修复策略并提前终止；通过调用次数、输出长度与 Token 预算准入约束迭代开销。
5. 使用 Pydantic 统一角色输出，落盘逐节点事件、原子状态快照及代码版本；建立 24 题、72 用例的自建评测集与四策略对照管线，完成 55 项回归测试，其中包含真实 Docker 集成验证。

简历版面不足时，把第 4、5 点各缩短半句即可；优先保留“客观验收、隔离执行、动态修复、可复现实验”四个特点。

## 3. 60—90 秒口述介绍

> 这个项目面向单文件 Python 和离线 LCEL 任务。我关注的问题是，模型生成的代码即使能运行，也可能输出错误；让模型自己审查，还可能错误地判定通过。
>
> 所以我把最终成功条件放在可信用例验收上。LangGraph 编排生成、执行、审查和反思流程，生成代码先经过语法与 AST 检查，再放进每用例独立的 Docker 容器执行，预期答案留在宿主侧比较。
>
> 修复时，首次简单错误直接反馈给生成角色，复杂或重复错误再进入审查和反思。我记录错误指纹、代码版本和失败轨迹，并设置重复失败、调用次数和 Token 预算限制，避免无限循环。
>
> 目前工程回归有 55 项通过，也验证了真实 Docker 的执行和资源配置。我还准备了 24 题的四策略评测管线，但尚未完成真实模型对照实验，所以目前能证明的是工程链路有效，不能宣称模型成功率已经提升。

## 5. 最后一个验收缺口怎么补

操作细节见 [测试指南](TESTING.md) 和 [评测指南](../benchmarks/README.md)。以下真实调用会产生模型费用；这份文档只提供命令，未执行它们。

```powershell
# 1. 检查 Docker 和固定输入执行，不调用模型
.\.venv\Scripts\python.exe code_assistant/doctor.py --probe

# 2. 凭据配置完成后，先跑一题真实模型端到端
.\.venv\Scripts\python.exe code_assistant/main.py --task examples/add.json

# 3. 先用两题检查真实评测链路
.\.venv\Scripts\python.exe code_assistant/benchmark.py --mode live --limit 2 --repeats 1

# 4. 确认小规模记录正常后，再执行完整对照
.\.venv\Scripts\python.exe code_assistant/benchmark.py --mode live --budget-profile attempts --max-attempts 3 --max-calls 9 --repeats 3
```

最后一条包含 24 × 4 × 3 = 288 个工作流，每个至多 9 次逻辑调用，理论上限 2592 次；预算按单工作流计算，并非整批共用。先根据小规模实际 usage 估算成本，再决定实验规模。

真实实验后同时看全体通过率、有效运行通过率、修复成功率、实际调用和 Token、耗时、排除的环境或模型异常数。若 adaptive 没有优于 direct，也应如实保留结论并分析适用场景；不要为了数字好看修改评测口径。
