# 大模型实习面试：项目精讲与追问

核对日期：2026-10-13，依据当前 v2 源码。本材料面向大模型应用 / Agent 工程面试，不代表科大讯飞内部题库。未提供具体 JD，因此不推断岗位偏训练还是应用。

## 1. 一分钟介绍

我做的是面向 LLM 生成代码的验证与修复 Agent 平台，当前限定单文件 Python 和离线 LCEL。用户通过网页插件或工作台提交代码和任务要求，选择静态诊断，或者提供人工可信用例做自动修复。后端由独立 Worker 执行 LangGraph：Planner 根据当前代码、观察和历史经验选择 Skill；确定性控制器校验计划依赖、权限和预算。复杂失败会经过审查、反思、再生成，候选代码只在受限 Docker 中运行，是否成功由宿主比较可信答案决定。状态通过 checkpoint 持久化，验证通过的经验可用于后续任务。我的重点是让生成过程可验证、可恢复、可追踪，而不是只把几个提示词串起来。

## 2. 用一道题走完整流程

目标：实现两个整数相加。原代码 `def solve(payload): return payload['a'] - payload['b']`，可信用例输入 `{"a":2,"b":3}`、预期 `5`。

1. 插件只在用户主动提取后读取可见代码块或选区，先预览，再提交目标、代码、模式和用例。不是自动读取整个对话或向聊天网站回复。
2. FastAPI 校验令牌、请求体、Pydantic 字段和幂等键，创建 queued 任务，返回 202 和 task_id。它不在 HTTP 请求里等待模型完成。
3. Worker 从数据库领取任务，更新租约和 fence；TaskService 开启心跳，以 task_id 作为 LangGraph thread_id。
4. intake 检查可信修复是否有 solve 入口和用例；缺失时 interrupt，保存 waiting_input。完整时检查 Docker 环境、保存原代码、检索兼容环境的经验。
5. Planner 可先选择 verify_cases。这里是合理的示例轨迹，并非模型每次必然选择同一条路径；也可以先 diagnose_python。
6. verify_cases 内部先静态检查，再向独立容器传入代码和输入，得到 -1。宿主比较 -1 与 5，产生 test_failure；规划器只看到净化后的失败类型和用例通过标记，不看到可信答案和原始 stdout。
7. Planner 选择计划中合法的 repair_python；若要替换已有计划，必须输出 revise_plan。逻辑失败会触发 Reviewer → Reflector → Coder，语法等简单错误直接调用 Coder。
8. 保存 candidate 产物与 diff 行数，清空已验证代码 hash。生成候选成功不代表修复成功。
9. 再次 verify_cases；所有用例通过后记录当前代码 hash，直接结束图，结果等级 verified。
10. TaskService 写入业务结果；启用记忆时提炼精简经验。Web 用 SSE 展示事件，插件轮询并显示最新候选。

## 3. 你必须能解释的实现

### 3.1 状态图不是四个角色各占一个节点

v2 图是 START → intake → plan → execute_skill → plan / END。Reviewer、Reflector、Coder 在 repair Skill 内调用。不要把旧版四节点图当成 v2 图。

AgentState 保存 code、original_code、plan、plan_version、completed_steps、observations、memories、调用账本、动作次数、deadline、verified_hash 等。可信 cases 保存在内部任务记录，通过 request_provider 供验证器读取，不进入这份图状态。

当前节点返回状态更新，列表通常显式用旧列表加新条目构造，不是靠消息 reducer 自动合并。当前执行串行，没有证明并行分支的状态合并正确性。

### 3.2 动态规划的具体边界

AgentDecision 只有 call_skill、revise_plan、request_input、finish。PlanStep 包含步骤 ID、Skill、依赖、目标和成功描述。控制器检查 ID 唯一、依赖只指向前面步骤、动作确属计划、依赖已执行。重规划更新版本并重置当前计划的 completed_steps；历史证据保留在 observations / 事件中。

completed_steps 表示动作执行过，不保证工具验证通过。success_criteria 是描述字段，没有通用可执行判定器；真正验收由确定性验证逻辑决定。这是应主动承认的实现边界。

非法动作累计 3 次停止；相同 Skill + 相同代码 hash 超过 2 次停止；还有动作、重规划、调用、Token 及时间上限。时间上限是节点间检查，不能当成所有外部 I/O 的硬实时截止。

### 3.3 为什么可以叫 Agent？为什么不夸大多 Agent？

它具备目标、观察、状态、动作选择、工具执行及反馈循环，所以超过了固定提示词流水线。但更准确的定位是 Planner 主导、多角色协作的受约束 Agent。Coder / Reviewer / Reflector 使用不同提示词和结构化契约，当前共享模型工厂，没有各自独立的长期目标和自治循环，也没有进行多模型投票。

角色拆分的假设是分离生成、局部审查和根因反思；收益可能被调用成本、延迟和同模型相关错误抵消。没有真实消融结果时不能说多角色一定更好。

### 3.4 Skill 与 Tool

Tool 是具体操作，例如 static_check、evaluate_trusted_cases。Skill 是任务能力包：说明、输入输出 schema、版本 / hash、工具白名单及执行流程。

四个 Skill：diagnose_python、repair_python、validate_lcel、verify_cases。Planner 先看目录摘要；选定后由 registry 校验参数与权限。当前修复 Skill 的完整说明进入 Coder 上下文，其他 Skill 主要执行固定工具分支；不是所有 Skill 都会启动独立 LLM，也不是任意 Markdown 都能变成可执行插件。

能力注册集中在代码里，说明在 SKILL.md，版本目前为静态 1.0.0，内容 hash 用于身份和环境过滤。不能宣传成动态热插拔 Skill 市场。

### 3.5 Pydantic 如何约束输出

调用链是角色 prompt → structured_call → with_structured_output(schema, include_raw=True) → parsed Pydantic 对象。解析失败或 parsed 为空会报错；raw 用于读取 provider usage。

Schema 约束字段、类型、枚举、长度等。新平台 StrictModel 禁止额外字段，但不要说所有旧角色 schema 都配置了 extra=forbid。AgentDecision 校验后还要经过计划依赖、工具权限和验收门禁，Pydantic 本身不理解代码正确性或业务权限。

具体使用 function calling 还是其他结构化协议取决于模型适配器；本项目代码未显式指定 method，不宜一口断言使用了某一种底层协议。

### 3.6 三种“记忆”不要混淆

工作状态：当前任务的计划、代码、近几次观察。Checkpoint：持久化执行状态和中断位置，负责恢复。长期经验：跨任务保存的简短失败类型、使用 Skill 与反思摘要，负责检索复用。Skill 文档属于程序性知识。

长期经验只接收 succeeded + verified + verified_hash 的任务，记录来源 task_id、owner 和 environment；environment 由 Docker 镜像身份和 Skill 内容 hash 构成。先过滤环境和归属，再检索。它不包含模型版本，仍可改进版本策略。

当前词项分支最多读取最近 200 条；PostgreSQL 另做 simple 全文检索。配置 embedding 后，用 pgvector 余弦距离检索相同 embedding 模型和维度的记录，再用 RRF 融合：score(d) = Σ 1 / (60 + rank_i(d))，最后取 3 条。

RRF 使用排序而非直接相加不同比例的相似度。向量目前存 JSON，查询时转 vector 做精确距离计算，没有 HNSW / IVFFlat，也没有大规模检索性能证据。simple 分词和朴素词项匹配对中文不理想；经验文本偏结构化、缺少充分语义，也可能降低召回。

embedding 默认关闭，失败降级；其费用尚未并入生成模型预算。写入验证门禁可以降低污染，但有限用例不能证明经验普适正确。经验只是参考，不能绕过权限和重新验收。

### 3.7 静态检查与隔离执行

静态：ast.parse、compile（编译而非 exec）、遍历 AST；检查语法、导入白名单、危险内建名和双下划线属性等。可以低成本拒绝明显不合规代码，但不能证明安全或业务正确。

动态：运行真实输入，才能发现除零、超时、资源问题、接口版本不兼容和逻辑错误。每用例独立容器；禁网、非 root、只读文件系统、去 capabilities、no-new-privileges、CPU / 内存 / PID 限制、小 tmpfs、输出限额、容器内外超时和清理。

AST 不是安全边界。Docker 是当前执行隔离边界，但容器共享宿主内核，不是绝对安全证明；公网多租户可进一步考虑更强隔离。不要声称该原型已经达到公网恶意代码服务标准。

宿主只把输入交给候选，预期答案留在宿主比较。单个有效 JSON 输出才进入比较，bool 和数值有专门区分。不符合 JSON 协议或结果不符都失败；当前数值比较没有通用浮点容差。通过用例仅说明通过这些用例。

### 3.8 恢复不等于自动重试任何东西

checkpoint 恢复图；业务 task 保存排队、取消、结果；action_runs 保存副作用动作结果。三个层次解决不同问题。

动作执行前写 started，返回结果后写 completed。同一动作 key 的 completed 结果可复用；只有 started 而无结果时，模型可能已收费，因此返回 unknown_action_outcome，不盲目重试。请求发出与数据库提交无法形成单一事务，不能宣称 exactly-once。

租约默认 90 秒，心跳每 10 秒。领取时 fence 递增，提交事件、结果和产物前检查归属与租约，阻止旧 Worker 覆盖新状态。当前还有全局单 Worker 限制，使用 SKIP LOCKED 不意味着已实现分布式高并发系统。fence 保护数据库提交，并不能撤销已经发生的外部调用。

取消是协作式：检查取消标记，Docker 轮询可终止进程并清理；已经发送的模型请求不保证立即撤销或免计费。人工恢复核对 version 和 interrupt_id 后补充入口 / 用例，使用 Command(resume=...)；不是任意修改任务需求的通用审批流程。

### 3.9 预算与观测

Planner、Coder、Reviewer、Reflector 都通过 call_agent 计数，不把“一轮”当作“一次调用”。调用前用提示词 UTF-8 字节、schema、余量及最大输出做保守准入，实际有 provider usage 时用实测值，否则使用预算预留值并标记 unknown。

字节估计不是厂商 tokenizer，预算不是货币账单硬上限。模型客户端关闭自动重试，降低隐藏重复调用。事件记录动作、计划版本、短理由、状态和用量，不需要保存完整隐藏推理过程。

SSE 适合后端单向推送；创建、取消、补充走 REST。事件有递增 seq，重连按 Last-Event-ID / after_seq 补拉，前端去重。插件当前用轮询，不要说插件也用 SSE。

## 4. 高频追问题卡

| 面试官问题 | 你需要说出的关键点 |
|---|---|
| 为什么不用一个大 prompt？ | 多轮需要外部观察、确定性验收、状态与副作用恢复；角色拆分的收益仍需对照验证 |
| 与 ReAct、Plan-and-Execute 有何关系？ | 先表达计划，再按观察逐步选择动作并可重规划；是受约束的混合实现，不宣称完整复现某论文 |
| 为什么选 LangGraph？ | 显式状态、条件路由、checkpoint、interrupt，避免自己实现全部持久化控制流；串行 while 也可实现基本循环 |
| 模型输出 JSON 为什么还出错？ | 格式、字段、类型可错；即便 schema 合法仍可能选错动作或写错代码，需要分层验证 |
| Reviewer 说通过能结束吗？ | 不能；可信修复只认工具验收和当前代码 hash |
| 为什么修复后清空 hash？ | 防止旧版本通过结果被新版本继承；所有证据绑定版本 |
| 记忆与 RAG 差别？ | 长期记忆是经验数据来源及生命周期；检索增强是使用这些数据构建上下文的方式，二者不互斥 |
| 反思一定提升效果吗？ | 不一定，同模型错误可能相关；按相同预算做消融，简单错误避免额外角色调用 |
| 为什么不展示 expected？ | 保持验收独立，减少按答案投机；代价是反馈较弱，可提供独立开发反例而保留 holdout |
| 页面代码含提示词注入怎么办？ | 不信任内容、严格 schema 和工具白名单、答案隔离、确定性门禁；prompt 提醒本身不是安全保证 |
| 执行进程崩溃怎么恢复？ | checkpoint + 业务状态 + 动作日志；不确定外部动作停止，明确安全优先的可用性取舍 |
| 多 Worker 怎么扩展？ | 当前未开放；需验证租约、并发事件序号、共享限流、背压、资源配额与隔离，再引入队列组件 |
| 为什么不用 Celery / Redis？ | 单机原型数据库队列减少组件与事务边界；规模提升后再评估吞吐和调度需求 |
| 如何接入讯飞星火？ | 主要改 get_llm 适配和配置，但必须重新验证鉴权、结构化输出、usage、超时和重试，不能保证仅改 base_url |
| 你训练或微调模型了吗？ | 没有，当前是推理侧 Agent 工程；LoRA、SFT 等作为基础知识另准备，不冒充项目经历 |

## 5. 效果评测应该如何回答

已有证据：完整 70 项 Python 回归，以及后续 15 项平台定向测试、2 项新增评测测试、3 项浏览器集成测试。15 项与完整回归有重叠，不要相加宣称 90 项独立测试。真实 Docker / PostgreSQL / MV3 已验证，模型使用固定替身。

真实 LLM 成功率、反思收益和记忆收益尚未实测。已有自建 24 题任务集与开发 / holdout 划分，但样本量和任务代表性有限。

已有 v2 实验组：legacy_adaptive、去掉修复 Skill 说明的 agent_without_skill_guidance、agent_skills、带冻结经验的 agent_skills_frozen_memory。第二组仍保留 Skill 调度协议，不是“完全无 Skill”；legacy 与 v2 存在多项差异，也不是纯规划单变量消融。

要测某模块的因果收益，应固定模型版本、任务、工具、预算、温度等，只改变目标模块，多次重复，并记录最终 holdout 成功率、调用数、Token、耗时、失败类别与不确定性。冻结跨题记忆，隔离同源变体，禁止从本次评测持续学习。无 usage 时标 unknown，不能算零费用。

当前主要可改进点：净化反馈过粗；状态 / prompt 截断是字符切片；完整历史与 checkpoint 可能增长；长期经验语义较弱；中文检索、向量存储和索引未优化；真实模型与网站兼容性验收未完成。

## 6. 推荐源码阅读顺序

1. `code_assistant/service/contracts.py`：先知道输入、动作和观察是什么。
2. `code_assistant/agent_v2/engine.py`：顺序阅读 initial、build、intake、plan、execute、tool、repair。
3. `code_assistant/agent_v2/model.py`、`utils/llm_runtime.py`：上下文、结构化调用、预算。
4. `skills/registry.py`、`memory/store.py`：能力权限与记忆检索。
5. `utils/acceptance.py`、`static_validation.py`、`docker_sandbox.py`：成功标准与隔离。
6. `service/tasks.py`、`persistence/database.py`：恢复、幂等、租约和结果提交。
7. `backend/app/main.py`：API 与 SSE；再读前端和插件。
8. `tests/test_platform.py`、`tests/test_platform_postgres.py`、`frontend/e2e/workbench.spec.ts`：从断言理解承诺的行为。

练习时不看代码回答：一个错误减法函数进入平台后经过哪些状态？谁可以决定结束？崩溃在哪个时刻会拒绝重试？记忆何时写入、何时读取？哪些指标是实测，哪些只是设计？这五个问题能连贯回答，再展开框架和算法细节。
